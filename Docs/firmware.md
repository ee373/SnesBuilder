# 共通BIOS・ファームウェア・ゲームパッケージ

Rev.0.7 / 基本設計段階

## 1. ARM側の内蔵メモリ

256KiBの内蔵フラッシュにはARM共通BIOS、65C816用SFC側BIOSイメージ、ブートローダ、制御ライブラリを配置する。SFC側BIOSは外部NORに保持せず、起動・再起動のたびに外部SRAM末尾8KiBへ展開する（収まる容量で設計する）。

| 機能 | 内容 |
|---|---|
| ブートローダ | 起動、USB更新 |
| 初期化 | GPIO、UDB、DMA |
| NORドライバ | 読み出し、消去、書き込み |
| SRAMドライバ | アドレス変換、メモリアクセス |
| microSDドライバ | SPIによるアクセス |
| ファイルシステム | ゲームファイル管理 |
| バス調停 | SFC・ARM間の所有権制御 |
| コマンド処理 | SFC通信 |
| ゲームローダ | ARMプログラム展開 |
| セーブ管理 | SRAMとmicroSDの同期 |
| 共通ライブラリ | ゲーム向けAPI、数値演算 |

64KiBの内部SRAMにはゲーム固有のARMコード、ゲームワークメモリ、BIOS作業領域、転送バッファ、スタックを配置する。各領域の容量配分は未確定である。

```text
PSoC Internal SRAM : 64KiB
+-------------------------------+
| ARM Game Program              |
+-------------------------------+
| Game Work Memory              |
+-------------------------------+
| BIOS Work Memory              |
+-------------------------------+
| Transfer Buffer / Stack       |
+-------------------------------+
```

ARMゲームはCortex-M3向けのネイティブバイナリとして生成し、SRAMへロードして所定のエントリポイントから実行する。外部メモリ、microSD、通信レジスタ、DMA等は共通BIOS APIを通じて利用する。ABIとしてロードアドレス、エントリポイント、スタック、API呼び出し規約、BIOSバージョンを定義する（未確定）。

## 2. microSDとUSB/SWD

microSDはSPI（SCK、MOSI、MISO、/CS）で接続する。出力3信号は既存3SBの第4グループで5V→3.3V変換し、MISOは3.3V SIOへ直結する。SPIはUDBによるハードウェア実装（高速SPI候補は18Mbps級）またはARMによるGPIOソフトウェア実装（同じピン配置）とする。メモリバス、通信、FIFOのUDB資源を優先して選択する。PSoC 5LPには固定機能SPI/SCBが存在しない。ソフトウェア実装時はP12の他のメモリ制御ビットを保持する。FAT系ファイルシステムを想定し、ゲーム、リソース、設定、セーブ、既存ROM向けパッチを保存する。

Full-Speed USBはPCとの通信、共通ファームウェア更新、ゲーム転送、デバッグ情報の取得、設定変更、開発用データの読み書きに利用する。USBプロトコルとPCツールはSDKと並行して定義する。

PSoCの初回プログラム書き込み、デバッグ、USBブートローダの復旧にはSWDを利用する。電源条件は[power-cic.md](power-cic.md)を参照する。

## 3. ゲームパッケージ

ファイル構成の暫定案:

```text
/
├── system/
│   ├── config.json
│   └── patches/
└── games/
    └── example_game/
        ├── manifest.json
        ├── game.sfc
        ├── arm.bin
        ├── assets.bin
        └── save.srm
```

| ファイル | 内容 |
|---|---|
| manifest.json | ゲーム識別情報と実行条件 |
| game.sfc | 65C816用プログラム |
| arm.bin | Cortex-M3用ネイティブコード |
| assets.bin | 画像・音源・各種リソース |
| save.srm | セーブデータ |
| config.json | カートリッジ設定 |
| patches/ | 既存ROM向けパッチ |

manifestにはゲーム名、バージョン、ゲームID、必要なBIOSバージョン、ARMコードの実行条件、ROMマッピング・有効容量、SRAM使用容量、リソース情報などを記録する。正式な形式とフィールドはSDK仕様として確定する。

## 4. 開発カートリッジの起動処理

1. 電源投入後、CIC認証とPSoC起動を開始する。PSoCの初期化前にSFCが先行動作してもよいが、PSoCのメモリ制御出力は初期化まで非選択・High-Zを維持し、バス競合を防ぐ。
2. PSoC起動後、SFC側/RESETをLowへアサートして再リセットし、そのまま保持する。この制御はP15[1]の入力兼オープンドレイン化を第一候補とし、SFC側の電気的適合性を実機で確認する。
3. SFCをリセット保持したまま、PSoCがUDB/GPIO/メモリバスを初期化し、ARM所有で内蔵FlashのSFC側BIOSを外部SRAM末尾8KiB（0x1E000～0x1FFFF）に展開する。末尾領域はセーブ対象外なので退避・復元しない。
4. ARMがBOOT_MODEを設定し、UDBの固定値応答を有効にする。CPU $00:FFFC/$00:FFFDではリセットベクタ$8000、$00:8000～$00:8003では`JML $2F6000`の4バイトを返す。HiROM SRAMの$2F:6000～$2F:7FFFを有効にした上で、外部バス所有権をSFCへ返す。
5. SFCの/RESETを解放する。65C816はUDB固定値応答から6バイト相当のブートデータを取得し、$2F:6000（SRAM物理0x1E000）のBIOSへジャンプする。起動時はSlowROM設定を基本とする。
6. BIOSは起動直後に$5000通信レジスタを介してARMへBOOT_MODE解除を要求し、解除完了を確認する。通常NORマッピングを復帰させるが、実行中のHiROM SRAM窓は維持する。必要な割り込みベクタを準備してから割り込みを許可する。
7. BIOSがStart＋Selectの同時押しを確認する。同時押しならBIOSメニューを継続し、それ以外ならNORに保持された前回のゲームの起動へ進む。ゲーム選択・microSD書き込みもBIOSから実施できる。
8. ゲームROMの書き換えが必要な場合はSFC側ローダ／待機コードを本体WRAMへ転送し、既存のバス調停に従ってARMに外部メモリを渡す。ARMがNOR書き込み、ゲーム用ARMコード展開、必要なセーブデータ読み込みを行う。
9. 通常ゲーム起動時はSFC本体WRAM上の切替ルーチンからARMへ要求を出し、ARMが隔離状態でゲーム用HiROM/ExHiROM、ROM容量・SRAM・通信の設定を適用する。SFCへのバス返却と切替完了を確認後、WRAMコードがゲームROMのリセットベクタを読み出し、そのエントリポイントへ移行する。
10. ゲーム動作中にBIOSへ戻る場合も、ARMがSFCを再リセット保持した状態でSRAM末尾へBIOSを再展開し、BOOT_MODEを設定してから/RESETを解放する。

NORの書き込み中はSFCがWRAMコードを実行し、ロード画面を表示できる。ROMに同一ゲームが残っている場合は識別情報を確認して書き込みを省略する。

UDBが固定応答する6バイト相当のブートROMを採用し、SRAMへ展開するのはBIOS本体のみとする。リセット保持中にBIOS全体をSRAMへ展開するため、PSoC初期化およびBIOS展開の所要時間はSFCの再リセット保持期間で確保する。初回のSFC先行動作は最終的なBIOS起動より前に強制リセットして解消する設計だが、初期化前のバス競合、P15[1]からのリセット再アサート、最小リセットパルス幅、CICとの相互作用は回路・実機で確認する。

## 5. セーブ管理

セーブはバッテリーバックアップ付きSRAMに保存する。次回起動時やゲーム切り替え時にmicroSDの対応ファイルへ書き出し、新しいゲームのセーブを読み込む。

PSoCの内蔵EEPROMには最後に実行したゲームの識別情報、SRAM使用状況、管理情報を保持し、SRAMに残っているデータがどのゲームに対応するかを判定する。ゲーム固有のセーブ領域の大きさや配置はSDK・パッケージで定義する。

## 6. 実行時USB通信と外部ホスト駆動

2026-11-17の検討によるソフトウェア拡張方針。現行Rev.0.7のハードウェア（8MiB NOR、128KiB共有SRAM、64KiB内部SRAM、双方向FIFO・DMA、USB、SWD）を維持し、追加IC・GPIOを前提としない。PSoCはFull-Speed USBデバイス、PCまたはRaspberry PiがUSBホストになる。「USBホストモード」は外部ホストがゲームを主導する動作を指し、PSoCをUSBホストとして動作させる意味ではない。

| 動作モード（構想） | 外部ホスト | ARM | SFC |
|---|---|---|---|
| ネイティブ | 不要 | ゲーム処理・演算 | ゲーム処理・映像・音源・入力 |
| USBホスト駆動 | ゲーム・描画・音源データ生成 | USB・FIFO・データ変換 | PPU・APU制御・入力 |
| ハイブリッド | ゲーム処理・高度な演算・ネットワーク等 | ゲーム処理・展開・変換 | ゲーム処理・映像・音源・入力 |

USBホスト駆動時はNORに格納したSFC側制御プログラムを動作させ、ARM側の共通BIOSまたは専用通信プログラムが外部ホストと通信する。実行中にROMを書き換えず、画像・音源・制御命令を受信し、コントローラ状態・実行結果・デバッグ情報を返送する。ネイティブ動作をUSB接続必須に変更しない。

USBのBulk IN/OUTを候補とし、内部SRAMのリングバッファ、USBエンドポイントとUDB FIFOの間のDMA、ARMによるプロトコル処理を組み合わせる。コマンド、データ種別、転送長、応答、フレーム番号、フロー制御、エラー復旧、接続断時の動作を定義する。具体的なエンドポイント構成、バッファ配分、DMAチャネル数、ゲームABIとの共存は未確定である。通信帯域と転送方法は[communication.md](communication.md)を参照する。

USBホスト駆動機能は現行回路の応用であり、実装・動作確認済みの機能ではない。

## Rev.0.7 ROM容量変換と追加音源

ゲームローダはROM容量を1MiB単位で扱う。1MiB未満のROMは元イメージの正しいミラー規則に基づき1MiBまで複製し、1MiB以上の整数MiB容量ではブロック数を設定してROMハードウェアミラーリングを利用する。整数MiB以外では不足部分を事前に補完する。HiROMは1～4MiB、ExHiROMは1～8MiBに対応する。NORの差分/キャッシュ再利用とセクタ消去・バッファ書込み最適化は従来通り継続する。

追加モノラル音声ドライバはPSoC内蔵DVDAC、タイマー、DMA、内部SRAMのサンプルバッファで構成する。初期評価は10bit・32kHz PCM、12bitモードは低帯域用とする。外部音声入力のアナログレベル、起動/停止時のポップノイズ、DMA負荷は実機で評価する。標準SPC700/BRRストリーミングも引き続き利用できる。[audio.md](audio.md)参照。
