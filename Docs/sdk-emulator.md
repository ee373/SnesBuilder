# Rev.0.9 SDK・エミュレータ・USB連携

SFC側はPVSnesLibで65C816 HiROM/SlowROM最小サンプルを起動し、RISC-V側はVS Code＋AgRV SDK、FPGA側はPrepare LOGIC＋Supra Nativeを使う。SFCBuilder SDKは$5000通信の64アドレス窓、FIFO/IRQ、コプロセッサ演算、SRAM、メモリ所有権、NORローダをAPI化する。ares/bsnes/Snes9x等のエミュレータはROM4形式・容量ミラー・SRAM・通信・演算要求のゲームから見える挙動を再現する。

USB Full-SpeedではAG32をデバイス、PC/Raspberry Piをホストとし、画像・音声・操作・デバッグを双方向転送する。USBが接続されなくても通常ROMを起動可能とする。

## カートリッジからSFC本体への映像転送

**3DデモとUSB映像転送モードは、SFC側の表示方式を共通化する。** 両者とも本命として[3DデモのMode 3・BG1 8bpp統一方式](prototypes/3d-demo/README.md)を採用し、V-BlankのVRAM部分更新と、H-BlankのCGRAM/BG1VOFS HDMAを併用する。映像を作る入力元だけが異なる。3DデモはRISC-Vのレンダリング出力を使用し、USB映像転送モードはPC/Raspberry Piが送信した映像を使用する。

```text
[カートリッジ側]
  3Dデモ: RISC-Vレンダリング ─┐
                               ├→ 画像整形・8bppタイル/CGRAM/HDMA素材
  USB映像: PC等 → USB → AG32 ─┘
                                        ↓
                               FPGA AHB・共有MEM調停
                                        ↓
                                   外部共有SRAM
                                        ↓ SFCカートリッジバス
[SFC本体]                          65C816
                              ┌─────────┴───────────┐
                              ↓                     ↓
                         V-Blank DMA         H-Blank HDMA
                              ↓                     ↓
                         VRAMの8bppタイル   CGRAMのRGB555色とBG1VOFS
                              └─────────┬───────────┘
                                        ↓
                                      PPU表示
```

RISC-V/FPGAやUSBコントローラがSFCのPPUへ直接書き込むわけではなく、**65C816が共有SRAMからDMA/HDMAでPPUへ投入する**。映像本体とDMA/HDMA転送素材は共有SRAMで受け渡す。一方、$5000の64アドレス通信窓・FIFO・IRQはコマンド、転送準備完了、フィールド同期、エラーなどの制御通知に利用する。初期各4バイトのFIFOを画素フレームバッファとして扱わない。詳細は[bus.md](bus.md)および[communication.md](communication.md)を参照する。

### 共通の映像形式と転送量

採用した設計目標は次のとおり。これは**論理画像情報量と帯域上の目標**であり、インターレース表示位置、実際のHDMA書込時間、目標解像度での映像更新は実機未検証である。

| 項目 | 基本目標 | ストレッチ目標 |
|---|---:|---:|
| 論理画像解像度 | 116×112 | 124×112 |
| V-Blankで更新するBG1 8bpp領域 | 88×112 | 96×112 |
| HDMAでCGRAM色を更新する領域 | 28×112 | 28×112 |
| 1フィールドで新規に与える画像ライン | 56 | 56 |
| VRAM 8bppタイルデータ/フィールド | 4,928 B | 5,376 B |
| CGRAM RGB555色情報/フィールド | 3,136 B | 3,136 B |
| 表示の設計目標 | NTSC約60フィールド/秒、偶奇2フィールドで論理112ライン | 同左 |

8bpp側は199色の共通パレットを参照するタイルの画素番号を更新し、28画素側は固定タイルの画素番号が参照するCGRAMのRGB555色をA/Bの2組で交互に更新する。通常パレット199色、動的28色×2、透明番号0の合計256エントリを用いる。BG1VOFSのHDMA変更によって4走査線あたり1画像ラインを参照する。7色/走査線のCGRAM更新と偶奇フィールド表示の成立は実機で確認する。

### USB映像転送モードの処理順

1. PC/Raspberry Pi側で映像の入力・必要なスケーリングとフレーム時刻の管理を行い、AG32へUSB Full-Speedで送る。**USB上の画素符号化・圧縮方式、転送パケットと制御プロトコルは今後具体化する**が、表示側の8bpp統一・CGRAM HDMA方式は共通仕様として固定する。
2. AG32側で受信素材をSFC向けの**8bppタイルのビットプレーン**、**28画素/画像ラインのRGB555色情報**、**CGRAM A/B更新およびBG1VOFS用HDMAテーブル**に整形する。変換をホスト側とAG32側のどちらへ配置するかはUSB負荷・内蔵SRAM使用量を実測して決める。
3. RISC-Vが共有SRAMへ転送素材を配置し、FPGAで共有MEMの所有権を調停する。65C816は転送準備完了の通知に基づき、V-BlankにVRAMをDMA更新し、可視期間にCGRAM/BG1VOFSをHDMA更新する。
4. フィールド切替時には画像素材、HDMAテーブル、A/Bパレットの表示参照、転送中バッファの所有権を同期し、書き込み途中の画像を表示させない。USB受信が遅れた場合は**完成済みフィールドを保持する**方針とし、欠落フィールドの扱いや遅延は実装検証で決める。

この共通化はSFC側の画面更新方式の統一であり、USBの12Mbit/sをそのままPPU書込帯域とするものではない。USB転送量にはプロトコルやバッファのオーバーヘッドがあり、SFC側ではV-Blank DMAとH-Blank HDMAの実行時間、65C816の制御時間、共有MEMの調停が上限となる。USB配信デモでは受信帯域だけでなく、フィールド完成時刻・VRAM DMA完了・CGRAM更新成功数・表示遅延を測定する。

## ゲーム固有RISC-VプログラムとFPGA演算器

SFCBuilderの共通ファームウェアはAG32内蔵Flashに常駐し、ゲームパッケージのRISC-Vコードは外部8MiB NORから内蔵SRAMへ展開して実行する。ゲーム用GCCリンクは内蔵SRAMを実行アドレスとし、共通Flash側のRAM領域と重複させない。共通ファームウェアのサービスは固定ABI/API経由で利用し、SFC側の65C816コードは既存の$5000通信窓とFIFO/IRQを通じてRISC-V側へ処理を要求する。

RISC-VがFPGA内の演算アクセラレータを使う場合は、内部AHBにメモリマップした入力・制御・状態・結果レジスタをMMIO経由で操作する。演算器のアドレスは生成トップで確定する。ゲームパッケージには65C816 ROM・RISC-V実行イメージ・リソース・セーブ定義の配置情報を持たせ、NOR物理容量8MiBの範囲内で格納する。
