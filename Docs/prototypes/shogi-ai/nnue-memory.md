# NNUE評価関数のNOR格納とCortex-M3での演算計画

作成日: 2026-11-17 / 状態: 実装前の検討・実測待ち

## 1. 目的と候補

最終的な高棋力候補は「つようら王11micro」の学習済み評価関数を利用した、SFCBuilder上で独立実行する将棋AIである。既存の学習済み評価関数に、Cortex-M3向けの合法手生成、探索、NNUE評価実装を組み合わせる。評価関数だけを移植しても思考エンジンにはならないので、探索・局面管理・時間制御も開発する。

ARMはCortex-M3最大80MHz、内部SRAM64KiB、FPUなし、外部NOR 8MiB・外部SRAM128KiBという条件を維持する。PC上で機械学習とデータ前処理を行い、実機では整数演算による推論・探索だけを実行する。

## 2. 圧縮して格納する理由

ネットワーク構造 `SFNN_ka2_2048_8_64_progress8` の特徴変換層は1,791入力特徴量×2,048要素の16bit重みを含む。特徴変換層のバイアスを含む生データ量は

```text
(1,791 input features + 1 bias) × 2,048 elements × 2 bytes
= 7,340,032 bytes = 7 MiB
```

となる。後段の8組のネットワークや進行度データも存在する。進行度ファイルは公式形式で125,388個のfloat64、計1,003,104バイトであり、通常の読み込み時にはQ16固定小数点整数へ変換する。これを事前に32bit整数化すると501,552バイトに減る。

会話中の構造計算に基づく参考値:

| 項目 | 概算 |
|---|---:|
| 特徴変換層の重み＋バイアス | 7,340,032 bytes |
| 後段ネットワーク8組 | 約150 KiB |
| 進行度パラメーターを32bit整数化 | 501,552 bytes |
| **圧縮を解いた場合の合計** | **約7.62MiB** |
| NOR全容量 | 8MiB |
| 全展開後の残容量 | 約0.38MiB |

全展開するとSFC側ゲームROM（例: 512KiB）、ARMコード、ヘッダ、その他リソースの同居が困難になる。**そのため、特徴変換層の重みを圧縮したままNORに格納し、必要になった特徴量の列のみ復号する**ことを標準案とする。

配布時の「約4.5MB」は会話で扱った公称の参考値であり、選定した実際の `nn.bin`、別ファイルの `progress.bin`、索引・ヘッダ・配置アラインメントを含めた合計サイズは実ファイルで確認する。上記の全展開サイズも実バイナリのデコード結果ではない。

## 3. NOR格納形式（設計案）

特徴変換層の各特徴量に対応する2,048個の重みを、独立して復号できるブロックに再構成する。形式例:

```text
Shogi model package (NOR)
+-------------------------------------------+
| header: version, architecture, CRC, size  |
+-------------------------------------------+
| feature_offsets[1791] (32bit x 1791)      |  約7 KiB
+-------------------------------------------+
| feature weights: compressed blocks        |  各ブロックで独立復号
+-------------------------------------------+
| FT biases: int16[2048]                    |
+-------------------------------------------+
| 8 sets of later fully connected layers    |
+-------------------------------------------+
| progress parameters: Q16 int32[125388]    |
+-------------------------------------------+
```

Signed LEB128を利用する実ファイルが入力であれば、PC上の変換器で要素ごとに復号してからブロックごとに再符号化する。ブロックのデータ先頭を32bitオフセットで記録すれば、ランダムな特徴量アクセスのたびに先頭から全ストリームを復号せずに済む。元の重み値と量子化を変化させない変換を第一段階とする。

ブロック境界・圧縮方式・読み出し効率は実データの分布とNOR速度の測定後に決定する。16bit生データへの展開、可変長整数のまま逐次復号、2段階圧縮、頻出特徴量キャッシュを測定で比較する。NAND等の外部記憶ICや追加GPIOを必要としない方式を優先する。

## 4. 差分更新の処理

NNUEの特徴変換層はAccumulatorを保持し、局面の変化に対応する重みを加減算する。駒を取らない通常の移動を「旧特徴の除去＋新特徴の追加」が先手・後手の両視点に各1組発生するものとして計算すると、

```text
2 (perspectives) × 2 (removed + added) × 2,048 weights
= 8,192 weight elements
= 16,384 bytes (raw int16)
```

となる。取る手・成り・打つ手・玉移動や特徴量の定義によって参照数が変化するため、これはベンチマーク用の基本ケースである。玉位置などの影響でAccumulator再計算が必要な局面は別に測定する。

復号した重みの列全体をSRAMへ保持する必要はなく、NORからバイトを取得し、signed LEB128を1個復号して直ちにAccumulatorに加算または減算できる。2視点のAccumulatorは `2 × 2,048 × 2 = 8,192 bytes` であり、内部SRAMに置く。探索深度に比例するAccumulator複製を無制限に内部SRAMへ置かず、探索スタックの実装方式を設計する。

評価の後段には、進行度で選択したネットワーク1組を適用する。8組全部の後段演算を毎局面実行する構成にはしない。

## 5. 時間見積もりの組み立て

固定した棋力・NPSを先に目標値として置かず、実測値を次式で分解して見積もる。

```text
T_eval = T_NOR_read + T_decode + T_acc_update
       + T_progress + T_dense_layers + T_other
T_search = T_movegen + T_make_unmake + T_eval + T_hash + T_prune + ...
```

仮に通常移動で8,192個の重みが必要で、圧縮平均1.1byte/要素、NOR実効2MB/sとすると、読み出しだけで約4.5msを要する。1要素の追加復号が12 ARMクロックであれば80MHzで約1.23msを消費し、これらにAccumulatorの加減算と後段ネットワーク、局面管理・探索処理が加わる。**これは転送速度・復号コストとも仮定した例であり、実機測定結果ではない。**

評価関数の精度だけで強さは決まらない。限られた思考時間で探索できる局面数と、評価関数の有効性を両立させる。NNUEが低速な場合も初期段階で軽量評価関数や探索制御との速度・棋力比較を行い、最終的な採否を対局試験で決定する。

## 6. 内部・外部メモリの配置方針

| 領域 | 主な用途 |
|---|---|
| PSoC内部Flash 256KiB | 共通BIOS、制御ファームウェア |
| PSoC内部SRAM 64KiB | ARMゲームコード、実行スタック、2視点Accumulator、探索状態、バッファ |
| NOR 8MiB | SFCプログラム、ARMゲームイメージ、圧縮NNUE、定跡など |
| 外部SRAM 128KiB | 置換表、補助的な探索状態、セーブ |

内部SRAMはゲームコードとBIOS作業領域が競合するため、実バイナリのリンクマップで割り当てを確定する。外部SRAMとNORは同じバスを使用するので、頻繁に置換表を参照する場合のメモリ切り替えコストも測定する。

## 7. PC側で必ず検証する内容

1. 使用するNNUE実ファイルと対応するやねうら王のソースリビジョンを固定し、入力/出力/重み型と重みの順序を照合する。
2. 元データを読み出して、変換後パッケージの各特徴量列と全重み・バイアスが一致することを確認する。
3. 進行度のfloat64→Q16変換が元の実装と同じ整数値になることを確認する。
4. 複数の局面でPC版NNUEとCortex-M3向け整数実装のAccumulator・最終評価値を比較する。
5. 通常移動、駒取り、打ち、成り、玉移動、差分再計算などのケースでバイト数・CPUクロック数・評価時間を計測する。
6. SFCゲームROM・ARMコード・モデル・索引の合計がNOR 8MiB以内であることをイメージ生成時に機械的に検査する。
