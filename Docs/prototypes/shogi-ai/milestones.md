# 開発工程と合格条件

作成日: 2026-11-17 / 状態: 初期実装候補・技術実証案

## 1. 開発の基本順序

最初からつようら王11microを動かすのではなく、65C816側の通信パッチとARMネイティブコードの実行を先に確認し、最後に圧縮NNUEへ到達する。各段階の成果を次の段階でも使うことで、同一の将棋プログラムをSFCBuilderの初期テストから総合性能試験まで利用する。

| 段階 | 開発内容 | 完了条件 |
|---|---|---|
| M0: PC側解析 | 対象ROMのハッシュ・マッピング、ST018通信呼出し境界、盤面・指し手形式を調査 | 既存のゲーム画面から思考要求までの呼び出し経路と戻り値を説明できる |
| M1: SFC通信パッチ | 元の通信ルーチンをSFCBuilderの$5000レジスタ利用コードに交換 | デバッグ用の固定合法手を返してゲーム画面が進行する |
| M2: PC思考プロキシ | SFCBuilderのFull-Speed USBデバイス経由でホスト側AIに対局を委譲 | PCのAIから指し手が返り、SFCの画面に反映される |
| M3: ARM軽量将棋AI | 合法手生成、簡易評価、αβ探索、反復深化、思考中断をCortex-M3へ実装 | USBを外してSFCBuilder単体で対局できる |
| M4: 小規模学習済み評価関数 | 小容量NNUEまたは軽量評価関数で整数演算と差分更新を実証 | PC上の参照実装と局面評価値・最善手の整合性を検証できる |
| M5: つようら王11micro | NOR上の圧縮重みを特徴量単位で読み出して差分更新 | NOR 8MiBと内部SRAM64KiBの制約内で実機単独対局できる |
| M6: 最適化・棋力測定 | NOR読み出し・復号・探索を計測し改善、PCと自動対局 | 性能データと対局結果を再現可能な形で記録する |

M2のPC依存は開発上の一時的な状態であり、最終目標は外部PCを接続しないM5以降の実機単独動作である。M1～M2には、Rev.0.8本体の通信回路・USB実装が動作していることが前提となる。

## 3. テストの自動化

将棋を実際に指せなくても、思考エンジンの正否と棋力を評価できるようにする。

| テスト | 方法 | 判定 |
|---|---|---|
| 通信 | 固定パターン・長さ・CRC・タイムアウトの送受信 | 同一内容の再現・エラー復旧 |
| ROM変換 | エミュレータで元ROMとパッチ後の画面遷移・操作を比較 | 描画・入力・音声に意図しない差異がない |
| 合法手生成 | 既知局面と参照エンジンの合法手一覧を比較 | 合法手の集合が一致する |
| 指し手変換 | 打ち、成り、取り、王手、詰み、投了を確認 | UIとARMで同じ局面が維持される |
| NNUE | PC参照版とARM版の中間Accumulator・評価値を照合 | 整数化方式を揃えた上で結果が一致する |
| バス調停 | 思考中のWRAM実行、NMI停止、ROMアクセス監視 | 競合・フリーズ・誤読がない |
| 性能 | ARMクロック、NOR転送量、復号サイクル、NNUE評価、NPSを計測 | 同条件で反復測定できる |
| 棋力 | PC将棋エンジンとの自動対局、時間制御固定 | 勝率・推定レーティングを記録できる |

検証に使用する棋譜と問題局面には、千日手、持将棋、打ち歩詰め、二歩、王手放置、成り、不成、駒取り、時間切れを含める。初期段階では最低限の合法手生成と通信が完成してから棋力を比較する。

## 4. 性能の測定軸

定量評価では、`NPS`（探索ノード/秒）、`EPS`（評価局面/秒）、1局面あたりNOR読出バイト数・読出時間・復号クロック数・後段演算時間、平均/最大の思考時間、バス所有時間、メモリ使用量を分けて記録する。NNUEが遅い場合でも、どこに時間を消費しているかを特定できる。

最初の目標は「元ゲームからARMが返した合法手で1局を完了できること」とし、棋力目標は実測に基づいて後から設定する。アマチュア有段者に勝てるかどうかは、対局エンジンと探索時間を固定した測定で検証する。

## 5. 性能改善の候補

M5完了後は、圧縮データのランダムアクセス索引、展開時のメモリ読出し順序、頻出列キャッシュ、Accumulator更新、ループ展開、固定小数点積和、後段ネットワークのメモリ配置、探索枝刈りと置換表の配置を優先的に測定する。ARMによるNORへのアクセスは共通MEMバス所有権を取得して実行する。NNUE重みの高速転送やDMA支援を追加する場合は、PSoC側のFIFO・DMAとの資源競合を検証し、初期実装の必須要件には含めない。

## 7. 設計上の未確定事項

- 元ROMの通信ルーチン・盤面・合法手判定・難易度管理のどこまでを65C816側が担当しているか。
- LoROM原本のCPLDマッピングでの動作確認と、ゲーム資産を維持したままARM通信部を置換するために必要なパッチ。
- SFC側WRAMへ常駐可能な思考待機コードと、カートリッジROMを参照しない割り込み停止手順。
- つようら王11microの使用する正確な評価関数ファイル、構造・符号化方式、圧縮サイズ、変換後のデータ量。
- Cortex-M3でのNNUEと探索の実測時間、内蔵SRAMのスタック・コード・Accumulator配分。
- 元ゲーム・評価関数それぞれの再配布・パッチ頒布に関する利用条件。
