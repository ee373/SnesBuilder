# SDK・開発ツール・エミュレータ

Rev.0.8 / 基本設計段階

## 1. ツールチェーン

SFC側65C816とARM側Cortex-M3のソースを別々にビルドし、共通のゲームパッケージ生成ツールでまとめる。

```text
SFC Source               ARM Source
    |                         |
SFC Toolchain           ARM GCC Toolchain
    |                         |
 game.sfc                  arm.bin
    |                         |
    +------------+------------+
                 |
         Game Package Builder
                 |
         +-------+-------+
         |               |
      Emulator      SFC Hardware
```

ARMにはarm-none-eabi系ツールチェーン、SFC側にはHiROM・ExHiROM・LoROM・ExLoROMに対応する65C816用コンパイラ・アセンブラ・リンカを使用することを想定する。

## 2. SDKの共通機能

SFC側の通信アドレスは$00:5000～$00:501Fとし、割り込み・ポーリングを提供する。SlowROMを基本サポートとし、FastROMの120nsの実機条件が確認できた後に、FastROM指定のビルド設定を用意する。ROMバンク配置はローダが生成するNOR物理配置と一致させる。共通APIを定義し、開発者がAG256/UDBの内部構造やGPIOの詳細を理解せずに利用できるようにする。

- ARMへのコマンド、ステータスと応答の取得。
- 共有SRAMアクセス、メモリバス所有権制御。
- DMAと双方向FIFOデータ転送。
- microSDのファイルアクセス、セーブ管理。
- 固定小数点演算、座標変換、行列演算。
- 画像データ生成および展開。
- ゲームパッケージ生成。

サンプルプログラムは基本通信、共有SRAM、VRAM転送、固定小数点演算、2D描画、3Dポリゴン描画、microSD読み込みなどを想定する。ABIおよび正式APIは未確定とする。

## 3. エミュレーション方針

実機とPCエミュレータで同一のゲームパッケージを利用する。エミュレータではHiROM・ExHiROM・LoROM・ExLoROMのアドレス変換とローダ事前ミラー配置、独自通信レジスタ、ARM、共有SRAM、双方向FIFO、共通BIOS APIを再現する。PSoCの物理回路をすべて再現するのではなく、ゲームから観測できる外部仕様を互換実装する。

Cortex-M3命令実行にはUnicorn EngineなどのCPUエミュレーションライブラリを候補とし、ARM用ネイティブバイナリを実行する。仮想BIOS APIを介してメモリや通信機能を提供し、SFCエミュレータとの間でコマンド通信、処理時間を考慮した同期を実装する。

| SFCエミュレータ候補 | 目的 |
|---|---|
| ares | 独自拡張チップ実装 |
| bsnes | ハードウェア挙動を重視した実装 |
| Snes9x | 幅広い環境での動作 |
| Mesen | Lua等を使用した初期検証 |

aresやbsnesの既存ARM系拡張チップST018の実装をプロセッサ間同期の参考とする。MSU-1は独自拡張仕様を実機とエミュレータで共有する開発モデルとして参考にする。

正式なエミュレータ採用先は未決定であり、独自拡張チップ実装と実機との動作一致は未検証である。

## 4. 外部ホスト連携とHomebrew開発支援

ゲーム実行中のUSB通信をSDKの拡張機能として利用し、実機SFCをPCやRaspberry Piから操作可能なグラフィックス・サウンド・入力端末として扱う。ネイティブゲームを開発するための支援機能であり、現行のハードウェア構成と単体動作の開発目標を維持する。

想定する開発用途は以下のとおり。

- PC上の画像編集・変換ツールからタイル、パレット、スプライト、スクロール設定を送り、実機PPUによる表示を即時確認する。
- 音楽制作ツールからBRR音源、SPC700プログラムや再生指示を送り、実機のS-DSPによる音質を確認する。
- ROMの消去・再書き込みなしに画像、音源、マップ等を更新し、開発中のリソースを実機で確認する。
- コントローラ入力、ゲーム状態、デバッグログ、許可したメモリ・レジスタの値をPC側から取得し、テストやハードウェア挙動の検証に用いる。
- 開発初期にはPC側でゲームロジックを動作させ、実機の映像・音源・操作感を確認しながらARMや65C816へ処理を移植する。
- 外部ホスト、ARM、65C816が協調するゲームや、外部ホストによるネットワーク通信を利用するゲームを開発する。

ホスト側SDK/ライブラリ、転送プロトコル、SFC側制御プログラム、ARM側BIOS API、各機能のサンプルを想定する。USBホスト駆動の詳細は[firmware.md](firmware.md)と[communication.md](communication.md)を参照する。

## 5. 外部エミュレータを利用する実験的な応用

PCまたはRaspberry Pi上の既存SFCエミュレータでゲーム、マッパー、特殊チップを処理し、SFCBuilderのUSB通信を介してSFC実機を映像・音声出力とコントローラ入力に使用する方法も考えられる。SA-1、Super FX等の処理をSFCBuilderのUDBやARMに個別実装せず、外部エミュレータの互換性を活用できる。

完成フレームのタイル変換・転送方式と、エミュレータからPPU/APUの状態や描画命令を抽出して実機側で再現する方式を想定する。前者はUSB・VBlank・BRR転送帯域による解像度、フレームレート、色深度、音声品質の制約を受ける。後者はラスタ効果、レジスタ変更タイミング、HDMA、音源状態等の同期・再現が必要であり、エミュレータでのゲーム互換性がそのまま実機出力の完全互換性を意味するものではない。

外部コンピュータが必要となるため既存ROM実行の費用対効果は低く、SFCBuilderの通常のROM互換性の完成条件には含めない。実機出力、開発支援、ハイブリッドエミュレーションの実験用途として位置づける。正式な実装方式と性能は未検証である。

## 6. 初期開発環境をHiROMから開始する方針（2026-11-17）

第一段階は、既存の公開SDK **PVSnesLib** によって作成した通常の **HiROM / SlowROM** イメージを、SFCBuilderのNORからSFC実機で起動することとする。ARM拡張・BIOS・ゲームパッケージを完成させる前に基本ROMアクセスを検証する。Rev0.8のハードウェアは4種類のROM形式を対象とするが、最初のソフトウェア検証はHiROMから開始し、ExHiROM・LoROM・ExLoROM向けツールチェーン対応を段階的に確認する。

### 公開ツールチェーンと既知の課題

- PVSnesLibは専用GUI IDEではなく、C言語ライブラリ、816-tcc、WLA-DX（wla-65816 / wlalink）、素材変換ツール、GNU Makeで構成されるコマンドライン中心のSDKである。Visual Studio Codeはエディタ・ビルド操作環境として利用できる。
- 現行の公式ビルドルール [snes_rules](https://github.com/alekmaul/pvsneslib/blob/master/devkitsnes/snes_rules) はHIROMとFASTROMを選択できるが、ExHiROMに対応するマッピング設定を持たない。
- 開発者は2026-06-22に[Issue #332「ExHiROM support」](https://github.com/alekmaul/pvsneslib/issues/332)で未対応と回答し、WLA-DXでのROMバンク配置を調査事項としている。したがってExHiROM対応済みと仮定しない。

### 最初のHiROMテスト

1. PVSnesLibの既存サンプルをHiROM / SlowROMとしてビルドし、PCエミュレータで文字表示・入力を確認する。
2. 初回の小容量テストには512KiBのHiROM / SlowROMイメージを使用できる。ビルド設定例はHIROM=1、FASTROM=0、ROMBANKS=8（64KiB×8）、ROMSIZE=09、セーブなしならSRAMSIZE=00とする。PVSnesLibの使用リビジョンを固定し、ROMファイルの先頭に512バイトのコピー用ヘッダがないことを確認する。NOR書き込み前には元ROMのミラー規則に従い、選択したHiROM物理配置の必要なスロットにデータを複製する。
3. SFCBuilder側はCPLDのHiROM系モード、通常4MiB窓とSFCバス所有、SlowROM設定を選択し、ゲーム実行時の通信拡張の有無を設定する。NOR上の物理オフセット$00FFC0にはHiROMヘッダ、$00FFFCにはゲームのリセットベクタが存在するようにイメージを配置する。
4. ROMをNORへ書き込む最小限の手段を準備する。microSDローダやARMゲームパッケージの完成は初期要件に含めない。起動時はPSoCがSFC /RESETを再アサートして保持し、内蔵Flashから外部SRAM末尾8KiBへSFC側BIOSを展開する。BOOT_MODE中にCPLDがNORを非選択とし、PSoC UDBがリセットベクタと`JML $2F6000`を固定応答し、BIOSが$5000通信でBOOT_MODEを解除してから、WRAM上の切替ルーチンを介してNORのゲームリセットベクタへ移行する。CIC認証、バス安全状態、NOR読出制御も検証する。
5. 実機起動後は異なるHiROMバンクに配置したデータを読み出し、CPLDの上位アドレス線、NOR事前ミラー配置、SlowROMのアクセス時間を検証する。その後LoROM/ExLoROM/ExHiROMとFastROMの経路を検証する。

### ARM対応の追加方針

HiROM起動後、SFC側に$00:5000通信レジスタ、FIFO、共有SRAM、割り込み等の **SFCBuilder追加ライブラリ** を提供し、ARM側にはarm-none-eabi-gccと共通BIOS APIを使用する。当初はARMの固定テストプログラムをPSoC内部Flashに配置して通信を検証できる。最終的に65C816側game.sfc、ARM側arm.bin、リソースをまとめるビルド・パッケージ生成ツールへ拡張する。

初期段階でPVSnesLib本体の大幅なフォークは要求せず、既存Makefileに追加可能な独立SDKを優先する。ExHiROM対応を実施するときは、WLA-DXのバンク配置、ヘッダとベクタ、ライブラリのバンク参照、ARMバイナリとのNOR容量配分を合わせて検証する。

**現時点の課題**は、ツールチェーン版の固定、最初のNOR書き込み方法、CPLDとPSoCの安全な起動・所有権切替、実機SlowROM/FastROMタイミング、LoROM/ExROM対応リンカ、ARM ABIと統合パッケージ形式である。
